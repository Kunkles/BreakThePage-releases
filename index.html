Walkthrough · macOS

BreakThePage

A script breakdown tool that reads a screenplay, finds what each scene needs, and prints the paperwork — without the script ever leaving your Mac.

  • macOS 14+
  • Apple silicon
  • No network access
  • Encrypted projects
  • PDF & Fountain
  • 16.5 GB model, once

  • Nothing uploaded
White · the promise

The script never leaves this Mac

Scripts arrive under NDA, watermarked with the name of whoever they were sent to. Most breakdown tools want you to upload one. This one can't, and that isn't a policy — it's an entitlement the app doesn't have, enforced by macOS itself.

The model runs on your machine. The app is sandboxed with no outgoing network permission at all, so if it tried to open a connection the system would refuse it. Two things do need the internet — downloading a model, and checking for an app update — and both happen in separate helper processes that live inside the app bundle, have their own narrow permissions, and never see a page of script.

You don't have to take that on faith. The app can prove all three claims from the terminal:

$ /Applications/BreakThePage.app/Contents/MacOS/BreakThePage --verify-downloader PASS: helper answered. Installed: qwen3.8-27b-q4, qwen3.8-27b-q6 PASS: the helper is downloading (83585 bytes), so the network works in the helper. PASS: the app itself cannot open a network connection (macOS refused it).

What else is built in

  • Projects are encrypted at rest. Every project is AES-GCM encrypted with its own key, held in the Keychain. Nothing readable sits on disk.
  • Deleting really deletes. The key goes first, then the file. Even if a block of the old ciphertext survives somewhere on the disk, there is no longer anything that can read it.
  • Copy-restricted PDFs are asked about, not assumed. Almost every script a production sends forbids copying. The app tells you, explains that the text would be read into memory on this Mac and sent to no one, and waits for you to say yes.
  • The recipient's name is treated like script text. Distribution services stamp the recipient into the PDF's author field. It stays in memory and is never written to a log.
  • Signed, hardened and notarized. Developer ID signature, hardened runtime, notarized by Apple and stapled, so it opens without warnings and can be checked with spctl.
  • Updates are signed twice. Apple's notarization, plus a separate signing key that never leaves the developer's Keychain. A tampered download is refused by every copy of the app even if the server handing it out is taken over.
One honest exception

Anything you export is a plain file. A PDF on your desktop has none of the encryption the project has, and the save dialog says so every time. Keep exports where your production's rules allow.

Blue · getting started

Open a script, break it down

Open a PDF or a Fountain file and it becomes a project. A project holds more than one script, so a season of television lives in one place with each episode keeping its own breakdown.

The parser handles what real distributed scripts actually look like: scene numbers in either margin, A-pages, OMITTED, revision asterisks, coloured page headers, doubled headers, (MORE) and (CONT'D), watermarks, and front matter. It works out story days and measures each scene in eighths of a page.

Then press play — once you have a model, which is the next section. Scene by scene, the model reads the text and lists what the scene needs — cast, background, props, wardrobe, makeup, set dressing, vehicles, animals, stunts, effects, special equipment, and the light the script calls for. Every finding comes with the line it came from, so you can check it against the page rather than trusting it.

Breaking down a script takes a while too

Reckon on about 40 seconds a scene — so half an hour to an hour for an episode, and longer for a feature. There's a progress bar and a time remaining, scenes that are finished can be reviewed while the rest carry on, and you can run a handful first to see what you think before setting the whole script going.

Your Mac will get warm and the fans will come on. That's the graphics chip doing the work, which is the whole point of it running here rather than on someone else's computer. Nothing is wrong.

Two marks worth knowing

~ means the script implies it rather than saying it outright. † means the quote couldn't be found in the scene — read that one before anyone orders it.

Blue · first run

Getting a model, once

Before the app can read anything it needs a model, and the model lives on your Mac. That's the whole trick: nothing is sent anywhere because everything that does the reading is already here. It also means there's a download to get through first.

Set aside 30 to 40 minutes

The recommended model is 16.5 GB. On ordinary home broadband that's roughly half an hour to forty minutes. You do this once, not once per script, and not once per project.

Open Models in the toolbar and pick one. The download runs inside the app, with a progress bar and a speed, and you can keep working while it goes.

  • Qwen3.8 27B (4-bit) — 16.5 GB. The recommended one. Fits a 36 GB Mac and takes about 40 seconds a scene on an M4 Max.
  • Qwen3.8 27B (6-bit) — 22 GB. A little more accurate, slower, and wants a 48 GB Mac or more.
  • Qwen3.5 4B (4-bit) — 2.7 GB. Small and quick, for seeing how the app works before committing to the big download. It misses a lot more, so don't break down a real script with it.

If you want to try the app this afternoon and you're not sure about the space, start the 4B, have a look around, then set the 27B going before you go home.

What's happening while it downloads

  • The app isn't doing it. A separate helper inside the app bundle does the downloading. It's the only part with network permission, and it has never been given a way to read a script.
  • It resumes. Close the lid, lose the wifi, quit the app — it picks up where it stopped rather than starting the 16 GB again.
  • It's checked before it's used. The file only gets its real name once its size and SHA-256 both match what was expected. A half-finished or altered download is never loaded.
  • It stays put. Models live in a shared container, so they survive app updates and are shared between the app and the command-line tools. You can delete one from the same window to get the space back.
Pink · finishing it

The last part is yours

A model reads what the script says. That the practical is on a dimmer, that the car has to be a low-loader, that someone should check with stunts — none of that is on the page, and a breakdown isn't finished until a person has put it there.

  • Add anything the model missed: department, what it is, whose it is.
  • Change anything it found. Correcting the model's reading makes that entry yours, which is what stops the next run undoing the correction.
  • Write a note on any scene. It prints on the breakdown sheet, under the synopsis.
  • Rewrite the synopsis, after which it stops being the model's to replace.

Anything entered by hand survives a re-run and a revision. That's the only reason it's safe to type in: a re-run replaces the model's own findings and nothing else. On paper, hand entries carry no mark at all — the ~ and † exist to flag a machine's guess, and someone typing it in is the opposite of that.

Changes

Everything changed by hand is written down, with what it said before, and travels inside the encrypted project like the rest. Changes in the toolbar lists it, newest first. A breakdown gets handed between people over weeks and the question is always the same: did someone change this, or did the model always say that?

Yellow · finding things

Filtering: four ways to ask

A breakdown is only useful if you can get a question out of it. There are four different kinds of question, and each has its own place to ask.

1. The scene list

Search across headings, characters, story day and the name of anything found in the scene. Then group the results: script order, by location (the start of a shooting order), by story day, longest scene first, or by the colour of paper the scene is printed on.

2. Find ⌘F

Every distinct thing in the whole breakdown, once, with the scenes it appears in. This is the view that turns a list of scenes into an order: one lighter to buy, not four. It merges spellings, so zippo and Zippo lighter are one item, and it can look across every script in the project at once — which is how you find the prop that recurs in episode 6.

3. Ask the model

A plain question about the script — "which scenes have a gun in them?" — answered in about thirteen seconds. It works in two hops: it reads the scene summaries to decide where to look, then reads only those scenes in full. That's what keeps it fast on a hundred-page script.

4. The report filter

The one that decides what gets printed, and the most precise. Pick scenes the way you'd write them on a call sheet:

9, 12A, 40-52

A range takes in the pages inserted inside it, so 40-52 includes A48 — because that is what someone means when they write it. On top of that you can narrow by story day, location, paper colour, character, free text, to the scenes a revision changed, or to the scenes that have been broken down at all. For breakdown sheets you can also pick which departments print.

Two rules never change, whatever the filter says: anything you rejected is never printed, and findings you haven't looked at yet can be left out with one switch.

Green · getting it out

Exporting: paper people can use

⌘P opens Reports: the filter on the left, the real PDF in the middle, Print and Save at the bottom. The preview is the actual document, so where the pages break on screen is where they break on paper.

Breakdown sheets

One sheet per scene, in the order a sheet reads. Cast first, because that's what everyone looks at, then the rest roughly by who has to go and get it.

Camera and lighting

The same scenes read a different way: one row each, with the look, the light the script calls for, what changes the air — rain, fog, smoke — and what has to be brought, like cranes, mounts or effects. Under each row, the strongest beat in the scene and a one-line synopsis. It can be printed in story order, flashbacks first, which is how you plan continuity rather than schedule.

Printed at the top of every report

Whatever the filter was set to. A report on someone's desk that doesn't say what it left out is worse than no report at all.

There's a CSV export too, from the Character Arc window: a character's scenes in story order with light, weather and emotional beats, for anything you'd rather work out in a spreadsheet.

Goldenrod · revisions

Importing changes without losing your work

Scripts change. Sometimes a whole new draft arrives; sometimes it's eight reprinted pages in an envelope. Both are handled, and the difference between them matters more than it sounds.

A whole revised script

Scenes missing from the file were cut from the show.

Only the changed pages

Scenes missing from the file simply weren't delivered, and keep their breakdown.

Read a delivery of changed pages as a whole draft and it looks like 29 of 30 scenes were cut. So the choice is explicit, side by side with what each reading means, and switching between them re-compares straight away. You see the comparison before anything changes.

Half a scene is not a cut

This is the part that took real scripts to get right. A delivery holds only the pages that were reprinted, so a scene running over a page break arrives chopped off at the fold. Compared against the draft, that fragment looks like most of the scene was deleted — and splicing it in would delete it for real.

The app works out where each scene actually stops: a page either prints (CONTINUED) at the foot or its text simply runs to the bottom margin. A scene holding the foot of the last page you were given, with no next page to carry on to, is a fragment. So is one that reads straight through a gap in the delivery. Those scenes are listed as can't read: they keep the text and the breakdown they already had, and nothing is re-run against half a scene.

Pages that arrive as pictures

Distribution services sometimes flatten a page, so there's no text in it at all and every scene on it would simply be missing. Those pages are read with Vision, which ships with macOS and runs offline — the page still never leaves the Mac. It recovers the scenes and about 91% of the words: enough to break a scene down, never enough to quote, and marked as such wherever it appears.

The colour is kept

Productions reprint changed pages on a new colour each time — white, blue, pink, yellow, green, goldenrod, salmon, cherry, buff, tan, then round again on doubled colours — and the colour is how everyone refers to a change. "In the pink pages there's a second cop car."

So every scene keeps the colour of the paper it's printed on. It shows as the edge of the page down the side of the scene list, the way it looks from the side of a binder. Type pink in the search box and you get the pink pages. A scene running from pink onto yellow takes the yellow, because that's the page someone is holding when they ask about it.

When you accept a revision, changed scenes keep their old breakdown and are flagged rather than emptied, so nothing is thrown away silently. Then Re-run Changed breaks down only what actually moved.

Salmon · reference

Pictures, kept with the breakdown

Drag images onto a scene and they appear as a strip under its note. Pin them to the script as a whole for tone and palette, or to a single item — the engraved lighter rather than a lighter, which is the version that settles an argument on the day. Board shows everything pinned anywhere in the script, in script order.

They print as a look book: one page per scene, pictures large, with the heading, story day, cast, the light the script calls for and your note underneath. That's the prep-meeting document. Breakdown sheets stay a list to work from.

The camera's notes on where you were

A photograph off a phone records when it was taken and usually where. An app that says nothing about the production leaves your Mac can't quietly keep the coordinates of a location scout — they'd travel straight back out the first time anyone shared a look book.

So location, date, lens and camera all come out on the way in, and the import says which kinds it removed. Orientation stays, so portrait shots stay upright, and the pixels aren't re-encoded, so a JPEG doesn't lose a generation each time.

Attachments are separate sealed files beside the project, under the same key, so deleting a project still takes one key away and every picture in it goes dark at that moment. The same picture used on four scenes is stored once, and taking one off a scene doesn't delete it — it may be on another.

Cherry · staying current

Updates that know when to stop

The app looks for a new version once, at launch, while the splash is still up. If it's already current, the updater shuts down there and then — no scheduled checks, nothing polling in the background behind an app that reads scripts under NDA.

A failed check says nothing, because you didn't ask for it. Check for Updates… in the app menu runs the same check and reports what it finds.

Nothing downloads until you press the button. When it has, the app has to restart to swap itself in — no app can replace itself while it's running. You choose when that happens: Restart Now, or leave it and it goes in the next time you quit. Either way it won't close a script out from under whoever is reading it.

And when it goes wrong

If BreakThePage ever stops unexpectedly it writes a report before it goes, and Help ▸ Crash Reports… shows them. Nothing is sent anywhere — the app has no way to send it — so a report is a file on your Mac and you decide whether it ever leaves.

A report holds no part of any script. It's written in the clear, because a file that needs a key is useless once the thing holding the key has died, so it carries the version, the system, the Mac, a stack and a short trail of what the app was doing. The trail takes a fixed list of words rather than free text, so there's no way for a line of dialogue to end up in one.

The app still has no network access of its own; the updater's own helper does the fetching.
